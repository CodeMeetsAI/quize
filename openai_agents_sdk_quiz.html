1. Tools

6 questions
Q1
True / FalseMedium
A function tool is created by decorating a plain Python function with @function_tool, and the function's docstring and type hints are used by the SDK to automatically build the tool's name, description, and JSON argument schema.
  • True
  • False
Show Answer & Explanation
Correct Answer: True

Explanation

The @function_tool decorator inspects the function signature (parameter names, type hints, defaults) and its docstring to auto-generate the tool's schema that is sent to the model. This is exactly the pattern shown in the Panaversity tools examples, where a plain typed Python function becomes a callable tool with no manual JSON schema writing.
Q2
Single ChoiceMedium
How does an Agent know which function tools it is allowed to call during a run?
  • A. By scanning all Python files in the project for @function_tool-decorated functions.
  • B. By listing the tool functions/objects in the Agent's tools parameter when the Agent is constructed.

Correct Answer: B

Explanation

An Agent is explicitly given its tool set via Agent(..., tools=[tool_one, tool_two]). Only tools listed there are exposed to the model as callable functions during that Agent's turn.

Why other options are wrong

A: The SDK does not auto-discover decorated functions across a codebase. C: Handoffs transfer control between Agents; they do not attach tools. D: There is no global/implicit tool registry shared by all Agents.
Q3
Single ChoiceDifficult
During the tool-calling flow, after the model decides to call a function tool and the SDK executes the underlying Python function, what happens next in the agent loop?
  • A. The Runner immediately returns the raw tool output to the end user as the final output.
  • B. The tool's return value is appended to the conversation as a tool result, and the model is called again so it can use that result to decide the next step.
  • C. The Agent is discarded and a new Agent is started from scratch.
  • D. Execution pauses permanently until a human manually approves the tool result.
Show Answer & Explanation
Correct Answer: B

Explanation

This is the core of the agent loop: model → tool call → tool executes → tool result is fed back into the conversation → model is invoked again with that result in context. The loop continues until the model produces a final message with no further tool calls or handoffs.

Why other options are wrong

A: Tool output is not automatically the final output — the model still gets to interpret it. C: The same Agent instance continues running; it is not discarded. D: There is no built-in manual-approval pause for ordinary function tools.

    """Get the current weather for a given city."""

    name="Weather Agent",
    instructions="Help users with weather questions.",

If the user asks "What's the weather in Lahore?", what is the most accurate description of what happens?
  • A. The model directly writes Python code and executes it locally.
  • B. The model generates a tool call with argument city="Lahore"; the SDK runs get_weather("Lahore") and returns the string result back to the model, which then produces the final natural-language reply.
  • C. A handoff occurs to a "Weather" specialist Agent.
  • D. The docstring is ignored, so the model has no way to know what the tool does.
Show Answer & Explanation
Correct Answer: B

Explanation

The model sees the tool's generated schema (name get_weather, parameter city: str, description from the docstring), chooses to call it with the extracted argument, the SDK executes the actual Python function, and the string result is returned to the model as a tool result for it to compose the final answer.

Why other options are wrong

A: The model never executes arbitrary code itself — the SDK executes the registered function. C: No handoff is defined in this snippet, so no handoff occurs. D: The docstring is explicitly used as the tool description, not ignored.

2. Handoffs

6 questions
Q7
Single Choice · ScenarioMedium
An orchestrator Agent receives a request and decides that another specialist Agent should completely take over the rest of the conversation, including seeing the full prior history and replying directly to the user from that point on. Which SDK mechanism is most appropriate?
  • A. Wrap the specialist Agent with Agent.as_tool() and call it as a function tool.
  • B. Define the specialist Agent in the orchestrator's handoffs list and let the model trigger a handoff.
  • C. Clone the orchestrator Agent using clone().
  • D. Add an input guardrail that blocks the request.
Show Answer & Explanation
Correct Answer: B

Explanation

A handoff is exactly the mechanism for "complete takeover": the target Agent becomes the active Agent, inherits the conversation history, and owns the interaction going forward. That matches the described requirement precisely.

Why other options are wrong

A: Agent-as-a-Tool runs the specialist as a sub-task and returns control to the original Agent — it does not hand over ownership. C: Cloning just creates a configured copy; it does not transfer control mid-conversation. D: Guardrails validate input/output, they don't route conversations.
Q8

  • A. Agent B starts a brand-new conversation with no memory of anything said before the handoff.
  • B. Agent B sees the conversation history up to that point and becomes the Agent driving the rest of the run — it "owns" the conversation from that point onward.

Correct Answer: B

Explanation

The defining behavior of a handoff (versus Agent-as-a-Tool) is that the new Agent takes over as the active Agent for the rest of the run, with the conversation history carried over, rather than just returning a result to the caller.

Why other options are wrong

A/C: Handoffs are not a memory wipe or forced summarization by default. D: That describes Agent-as-a-Tool behavior, not a handoff — in a handoff, A stops driving and B takes over.

3. Runner & Runner Methods

6 questions
Q13
Single ChoiceMedium
Runner.run(agent, input) is best described as:
  • A. A synchronous, blocking call that must be used inside a plain script with no event loop.
  • B. An async coroutine that runs the full agent loop and must be awaited, returning a RunResult once the run completes.
  • C. A method that only works with streaming responses.
  • D. A method that requires an explicit handoff to be defined before it can run.
Show Answer & Explanation
Correct Answer: B

Explanation

Runner.run() is the primary async entry point: await Runner.run(agent, input) drives the full agent loop internally (model calls, tool calls, handoffs) and resolves to a RunResult containing final_output.

Why other options are wrong

A: That describes run_sync(), not run(). C: Streaming is handled by run_streamed(), a separate method. D: Handoffs are optional; an Agent with no handoffs runs fine with Runner.run().
Q14
Single ChoiceMedium
Why would a developer choose Runner.run_sync() over Runner.run()?
  • A. run_sync() is faster because it skips the agent loop entirely.
  • B. run_sync() gives a convenient blocking wrapper for use in simple, non-async scripts, internally running the same async loop and returning the result once it's done.
  • C. run_sync() disables tool calls and handoffs to keep execution simple.
  • D. run_sync() streams partial output token by token, unlike run().
Show Answer & Explanation
Correct Answer: B

Explanation

run_sync() exists purely for convenience in synchronous contexts (e.g., a quick script or a main() without async def); it runs the same underlying agent loop as run() and blocks until completion, returning a RunResult.

Why other options are wrong

A: It performs the identical loop, not a shortcut. C: Tools and handoffs still work normally. D: Token-level streaming is the job of run_streamed().

4. Agent as a Tool

5 questions
Q19
Single ChoiceMedium
What does calling some_agent.as_tool(tool_name=..., tool_description=...) accomplish?
  • A. It permanently converts some_agent into a handoff target only.
  • B. It wraps some_agent so it can be added to another Agent's tools list — the wrapped Agent runs as a sub-task and its output is returned as a tool result to the calling Agent.
  • C. It deletes some_agent's instructions and replaces them with the tool description.
  • D. It forces some_agent to always run with Runner.run_streamed().
Show Answer & Explanation
Correct Answer: B

Explanation

Agent.as_tool() is the SDK's built-in bridge that turns any Agent into a callable function tool: another Agent can invoke it like any tool, the wrapped Agent runs (its own mini agent loop) on the given input, and its result comes back as a tool result — the calling Agent stays in control.

Why other options are wrong

A: This has nothing to do with the handoffs mechanism. C: The Agent's own instructions remain intact; only a tool-facing name/description is added. D: as_tool() does not force any particular Runner method.
Q20

  • D. Only one of the two Agents can ever be included as a tool at a time.

Correct Answer: B

Explanation

Because both specialists are wrapped with as_tool() and placed in orchestrator_agent's tools list, the orchestrator stays the top-level Agent for the whole run. It can call one or both translation tools, receive their outputs as tool results, and then assemble the combined final answer itself — this is exactly the "translate multiple languages at once" pattern the Agent-as-a-Tool approach enables that a handoff cannot.

Why other options are wrong

What is the primary purpose of an Agent's clone() method?
